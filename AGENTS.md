# Agent Instructions

## Architecture
This repository implements an LLM agent that drives filesystem tools, plus a registry for MCP providers.

- **Tool Registry**: `src/tools/registry.py` defines `ToolRegistry` (register/unregister/dispatch/get_manual/list_tools) and `build_default_registry()`. The base tools are `read_file`, `list_dir`, `search_files`, `grep_files`, `write_file`, `patch_file`, `delete_file`, `move_file`, `run_command`. `src/tools/facade.py` is a backward-compatible facade over the `default_registry` (module-level `dispatch`/`get_manual`/`list_tools`, plus `register_tool`/`unregister_tool`). Each tool module exposes `get_manual()` and `dispatch(action, **params)`. Shared filesystem helpers live in `src/tools/_fs.py`.
- **Agentic Orchestrator**: `src/orchestrator/` is a *special tool* named `orchestrator`, built via `create_orchestrator_tool(registry, provider, memory, ...)` and registered into a `ToolRegistry` (see `src/main.py`). It drives discovery → planning → step-by-step execution → validation using only the tools in the registry. Actions: `run`, `discover`, `assess`, `plan`, `execute`, `pending`, `validate`, `undo`, `abort`. Mutations are snapshotted (`undo.py`) and rolled back automatically on failure; poor discovery aborts before planning. Because it is just another registry entry, removing it keeps the agent working with the base tools — low coupling.
  - **Greenfield seeding (`paths`)**: `run`/`plan`/`discover`/`assess` accept an optional `paths` list. When present, `Discovery.discover(..., seed_paths=...)` skips keyword search and turns each path into a candidate (`new_file` when missing, resolved against the orchestrator root). This is how the agent plans brand-new projects in empty directories, which keyword discovery cannot (it returns `poor` when nothing matches). The planner is instructed to create `new_file` targets with `write_file` at the exact seeded path, to give scaffold commands (`pip install`, `ng new`, `git init`) a `cwd` plus a generous `timeout`, and to `read_file` `docs/SPEC.md`/`docs/PLAYBOOK.md` first when they exist.
  - **Replace vs alter**: `src/orchestrator/impact.py` (`ImpactAssessor`) profiles each target deterministically — does it exist, is it a registered tool module, is the module contract (`MANUAL`, `SPEC`, `get_manual`, `dispatch`) intact — and classifies the change as `new` / `modify`. Existing files are planned via `patch_file`; `write_file` is reserved for new files or explicit rewrites (`"rewrite": true`). A plan that would `write_file` over an existing registered tool module without `rewrite: true` is rejected with guidance (re-plan). Rewrites are deep-validated at execution: the module is re-imported and the contract re-checked, otherwise everything rolls back. **Patch anchors**: `check_plan_steps` validates that a `patch_file` step's anchors actually exist in the target file (for `replace`, the `old` text; for `apply`, each hunk's context/removal block — line numbers are tolerated since matching is by content), rejecting hallucinated anchors before the plan is confirmed; if a patch still fails at runtime, `Orchestrator._execute` automatically re-plans with the failure as feedback (`exec_retries`, default 1) and re-executes instead of stopping.
  - **Tests in the plan (best effort, never mandatory)**: `ImpactAssessor` detects each target's language (python, typescript, javascript, java, kotlin, c, cpp, go, rust, ruby, php, csharp, swift, …), maps existing unit tests by the language's conventions and detects the project's test runner (package.json→jest, pom.xml/gradlew→mvn/gradle, go.mod→go test, Cargo.toml→cargo test, …). When a changed module is covered by tests, the planner adds a final `soft` `run_command` step running that command with the language's success marker — a failing test does NOT roll back the changes. When a framework is configured but nothing covers the target, the planner adds soft steps to create a suggested test file and run it. When no test setup exists, the planner does NOT auto-create a harness or run anything; the execution result reports `testing: {tested: false}` and asks the user whether to keep the changes or apply a custom test.
- **Agent Loop**: `src/agent.py` implements `Agent.run(user_prompt)` which iterates: build config prompt → `provider.infer` → parse tool call → `registry.dispatch` → record result, until a plain answer or `max_iterations`. The agent accepts a custom `registry` and optional `extra_tools`. **Confirmation flow**: when a dispatched result is `awaiting_confirmation`, the agent stores a `_pending_call` and prompts the model to relay the plan. On the next user turn it classifies the reply via `classify_followup` (`src/utils.py`): pure approvals ("sim", "pode ir", "continue") resume deterministically via `execute(confirm=True)` without a model round-trip; explicit cancellations call `abort`; ambiguous/conditional replies ("sim, mas muda X") go to the model with the pending plan as context. The orchestrator exposes `pending` to read the pending plan and `execute(confirm=True)` to resume it (no steps needed).
- **Provider Client**: `src/providers/opencode.py` implements `OpenCodeProvider`, an OpenAI-compatible client for OpenCode Zen (default model `big-pickle`, auth via `OPENCODE_API_KEY`). `infer(user_prompt, config)` sends a two-part prompt.
- **Config Prompt**: `src/utils.py::build_config_prompt()` assembles the configuration/system prompt (runtime environment via `build_environment_info()` — OS, python, workspace — plus tool list from the manuals, instructions and conversation history). `parse_tool_call()` extracts the tool-call JSON block from the model output. `extract_json_object()` is a general JSON extractor.
- **Memory**: `src/memory.py` defines the `Memory` class that stores conversation history and tool results. An optional `ContextCompressor` (from `src/context.py`) observes every add and summarizes old entries once the estimated token count reaches a threshold. Future work: on-demand tool context.
- **MCP Registry**: The `Registry` class in `src/registry.py` scans a directory for subdirectories containing a `run.sh` (Linux) or `run.bat` (Windows) file.
- **Navigation Subagent (`browser`)**: `src/navigation/` is a *special tool* built via `create_navigation_tool(provider, ...)` (see `src/main.py`) and registered into a `ToolRegistry`. It drives Playwright Chromium (headless) to navigate the web. The main registry holds **one entry** (`browser`) with a `run` action that delegates natural-language tasks to `NavigationSubAgent` (its own LLM loop over a private `ToolRegistry` of ~50 low-level browser actions) plus the low-level actions exposed directly (`open`, `snapshot`, `click`, `fill`, `evaluate`, `screenshot`, `assert`, `network`, `new_tab`, `switch_tab`, `close_tab`, `list_tabs`, `close`, ...). `BrowserController` is the thin sync layer over `BrowserSession` (multiple tabs; one active); `snapshot.py` produces a compact a11y/DOM tree with stable refs (`click e3`) that are   **scoped per tab** and persist until the tab's page changes.   **Isolation**: `BROWSER_ISOLATED=1` (or `create_navigation_tool(..., isolated=True)`) runs Chromium in a separate `src/navigation/worker.py` subprocess reached through a JSON-lines RPC `BrowserClient` (`src/navigation/ipc.py`) — the agent sees the same structured dicts in both modes, and a browser crash never takes down the agent.   **Page map**: `snapshot_map` (`url`/`refresh`) returns the last snapshot without re-crawling the DOM (cached per tab; `fresh`/`stale`/`mutated` by URL and DOM state; `found:false` when absent); with `BROWSER_SNAPSHOT_DIR` (or `create_navigation_tool(..., snapshot_dir=...)`) maps persist to `map-<sha256(url)>.json` so they survive `close`/restarts and are served with `source:"disk"` without launching a browser. **Video (opt-in)**: `BROWSER_VIDEO_DIR` (or `create_navigation_tool(..., video_dir=...)`) records a `.webm` per page (finalized on page/browser close; the file may be absent/size-0 while recording); `video` reports `{recording, path, finalized}` and `video_save` copies finalized recordings (`{saved, pending}`). `inspect(include=["trace"])` guarantees tracing, forces one frame and extracts the screenshots from the trace zip (`{path, screenshots, frames}`); `inspect(include=["video"])` reports recording status. **Ref invalidation**: an in-page `MutationObserver` (installed via `add_init_script`) marks structural DOM changes (`childList` only — typing/attribute edits do not invalidate), and `_resolve` blocks stale refs with `invalid_reference` when the DOM mutated or the URL changed since the snapshot (`BROWSER_MUTATION_INVALIDATE=0` disables blocking; `mutated` stays reported). **Headed + consent**: headless resolution is `headless` arg → `BROWSER_HEADED=1` → `BROWSER_HEADLESS` (default `1`); `pause` opens the Playwright inspector. `create_navigation_tool(..., proxy=ProxyConfig, site_credentials=..., credentials_store=...)` (from `src/navigation/credentials.py`; fallback file `.browser-credentials.json` / `BROWSER_CREDENTIALS_FILE`) enables a proxy and per-origin HTTP credentials that gate **all** navigation behind explicit human consent (`ConsentRequired` / `consent_required` until `consent confirm=true`; `revoke_consent` closes the session; `list_credentials`/`status` only ever reveal masked values). The gate lives in `BrowserController._ensure_page` before context creation (no browser is launched without consent). Credentials are applied as a single `http_credentials` dict (Playwright supports one per context) with `origin` + `send: "unauthorized"` (first configured origin wins; extra origins are reported but not applied).   See `docs/navigation.md`. Env vars: `BROWSER_HEADLESS`, `BROWSER_HEADED`, `BROWSER_ACTION_TIMEOUT` (10), `BROWSER_NAV_TIMEOUT` (30), `BROWSER_MAX_STEPS` (12), `BROWSER_ALLOW_HOSTS`, `BROWSER_BLOCK_HOSTS`, `BROWSER_ALLOW_EVALUATE` (1), `BROWSER_SCREENSHOT_DIR`, `BROWSER_TRACE_DIR`, `BROWSER_ISOLATED` (0), `BROWSER_CREDENTIALS_FILE`, `BROWSER_SNAPSHOT_DIR`, `BROWSER_MUTATION_INVALIDATE` (1), `BROWSER_VIDEO_DIR` (opt-in). Removing the entry (`registry.unregister("browser")`) keeps the agent working with the base tools.

## Adding a New Tool
1. Create `src/tools/<name>.py` defining the handler(s).
2. Define `MANUAL` (params and purpose, for the LLM) and a module-level `ToolSpec` with the action→handler map.
3. Export `get_manual()` and `dispatch(action, **params)`.
4. Register the module in `src/tools/registry.py::build_default_registry()` (or at runtime via `register_tool`).

## Using / Removing the Orchestrator
- Register: `create_orchestrator_tool(registry, provider, memory)` then `registry.register(tool.name, tool)`.
- Remove: `registry.unregister("orchestrator")` — the agent continues with the base tools unchanged.

## Adding a New MCP Provider
1. Create a new directory within the providers root.
2. Add a `run.sh` (for Linux) or `run.bat` (for Windows) file to that directory.
3. Ensure the script is executable and starts the desired service.

## Context Compression
`ContextCompressor` (in `src/context.py`) monitors the estimated token count of the memory and, once it reaches `CONTEXT_TOKEN_THRESHOLD`, summarizes the oldest entries (outside a recency buffer) via the provider and replaces them with a single `summary` entry. If the provider fails, it degrades to relevance-based truncation (n-gram embeddings). Wire it with `Memory(compressor=ContextCompressor(provider=provider))`; leaving the compressor off preserves the old behavior. Env vars:

- `CONTEXT_TOKEN_THRESHOLD` (default `6000`; `0` disables compression)
- `CONTEXT_TOKEN_FACTOR` (default `2.5`) — fallback estimator: words × factor
- `CONTEXT_KEEP_RECENT` (default `4`) — newest entries never summarized
- `CONTEXT_MAX_SUMMARY_CHARS` (default `2000`) — summary length cap

## Development & Testing
- **Dependencies**: Requires `mcp` (see `requirements.txt`). Runtime tools use only the Python stdlib.
- **Environment**: Uses a Python virtual environment (`.venv`).
- **Tests**: `unittest` — run with `.venv/bin/python -m unittest discover -s tests`.
- **Type checking**: `.venv/bin/python -m mypy src tests`.
- **Formatting**: `.venv/bin/python -m black src tests`.
- **Demo**: `.venv/bin/python src/main.py` (needs `OPENCODE_API_KEY` for the live agent demo).
- **Driver CLI**: `src/main.py` supports `--root <dir>` (chdirs the process into the project so `run_command` lands there), `--max-iterations N`, `--max-plan-steps N`, and `--prompt "..."` for a single non-interactive turn. E.g. `.venv/bin/python src/main.py --root /path/to/project --max-iterations 15 --max-plan-steps 12`. Set `CONTEXT_TOKEN_THRESHOLD=0` during long builds to avoid mid-build context summarization.
